# Intégration Continue (CI/CD) et Automatisation des Tests

Ce document marque l'aboutissement de l'industrialisation des scripts PowerShell. Il aborde la transition entre l'exécution manuelle (sur le poste de l'administrateur) et l'exécution automatisée (*headless*) au sein d'un pipeline d'Intégration et de Déploiement Continus (CI/CD). Il détaille la gestion des codes de retour, l'exportation des résultats Pester pour les orchestrateurs, et la structuration d'un flux de travail DevOps.

---

## 1. Le Changement de Paradigme : Qu'est-ce que la CI/CD pour l'Infra ?

Historiquement, un administrateur écrit un script, le teste sur son poste, puis l'exécute en production depuis sa propre session (ou via une tâche planifiée locale).

Dans une approche **DevOps / GitOps**, l'administrateur n'exécute plus les scripts lui-même :

1. **Il écrit le code PowerShell :** Script, module ou scénarios de test Pester.
2. **Il pousse (*Push*) ce code :** Sur un dépôt Git centralisé (GitLab, GitHub, Azure DevOps).
3. **Déclenchement automatique :** Cet envoi lance immédiatement un pipeline CI/CD.
4. **Exécution isolée :** Un serveur éphémère (appelé *Runner* ou *Agent*) télécharge le code, exécute la suite de tests et, si tous les indicateurs sont au vert, applique le déploiement en production.

> **Conséquence majeure :** Le script PowerShell doit être capable de s'exécuter de manière 100 % autonome, sans aucune interaction humaine, et de communiquer explicitement son succès ou son échec à la machine hôte (*le Runner*).

---

## 2. Le Langage Universel de la CI/CD : Les Codes de Retour (*Exit Codes*)

Un Runner CI/CD (qu'il opère sous Linux ou Windows) n'interprète pas visuellement la console. Si votre script PowerShell affiche une erreur rouge via `Write-Error` mais poursuit son exécution jusqu'au bout, le Runner considérera que la tâche a réussi (Statut : **Success**) et déploiera potentiellement une infrastructure instable.

Le pipeline se fie exclusivement au **Code de Sortie (*Exit Code*)** émis par le processus `powershell.exe` ou `pwsh` :

* **`0` :** Succès total (*Success*).
* **`1` (ou tout entier non nul) :** Échec critique (*Failure*).

### 2.1 Maîtriser le code de sortie d'un script

Pour qu'un script d'infrastructure communique fidèlement avec l'orchestrateur, il doit encapsuler sa logique dans un bloc `try / catch` avec une rupture immédiate sur erreur (`-ErrorAction Stop`) et forcer l'émission du code retour via le mot-clé `exit` :

```powershell
# =============================================================================
# Script de déploiement (deploy.ps1) exécuté par la CI/CD
# =============================================================================

try {
    Write-Host "Déploiement du service en cours..."
    
    # L'utilisation de -ErrorAction Stop est vitale pour déclencher le bloc catch
    Start-Service -Name "ServiceMetier" -ErrorAction Stop

    Write-Host "Déploiement réussi." -ForegroundColor Green
    
    # Émission explicite du code 0 pour valider le job (Success)
    exit 0
}
catch {
    Write-Host "ÉCHEC CRITIQUE : $($_.Exception.Message)" -ForegroundColor Red
    
    # Émission explicite du code 1 pour faire échouer le job (Failed)
    exit 1
}
```

## 3. Paramétrage Dynamique : L'Usage des Variables d'Environnement

Dans une chaîne CI/CD, aucun opérateur n'est présent pour saisir un mot de passe ou sélectionner un serveur cible. Ces informations contextuelles sont définies dans les paramètres du projet de l'orchestrateur (GitLab CI Variables, GitHub Secrets, Azure Pipelines Library) puis injectées dynamiquement dans l'environnement du Runner au lancement du conteneur ou de la VM.

Le script PowerShell doit récupérer ces données via le lecteur virtuel `Env:` :

```powershell
[CmdletBinding()]
param(
    # Le script récupère la variable $env:DEPLOY_TARGET injectée par la pipeline
    # En cas d'exécution locale hors CI, il bascule sur "localhost" par défaut
    [string]$ServeurCible = $env:DEPLOY_TARGET,

    # Récupération de l'identifiant unique de build ou de commit
    [string]$BuildVersion = $env:CI_PIPELINE_ID
)

Write-Host "Déploiement de la version $BuildVersion sur l'hôte $ServeurCible..."
```

> **Bonne pratique sécurité :** Pour les mots de passe maîtres et les jetons d'API, couplez cette technique avec le module `SecretStore` afin d'éviter toute exposition de valeurs sensibles en clair dans les journaux d'exécution de la CI/CD.

## 4. Intégration de Pester dans la CI/CD (L'Usine de Test)

L'objectif principal d'un pipeline CI/CD en infrastructure consiste à exécuter la suite de tests Pester de manière automatisée à chaque modification du code (*Shift-Left Testing*).

Cependant, le Runner ne peut pas interpréter le rendu vert ou rouge affiché par Pester dans la console. Il requiert un rapport structuré au format standardisé **NUnit** ou **JUnit (XML)**.

### 4.1 Exécuter Pester et générer un rapport XML pour la Pipeline

On configure l'objet de configuration `New-PesterConfiguration` afin qu'il produise un fichier de résultats directement lisible par l'interface web de GitLab, GitHub ou Azure DevOps :

```powershell
# =============================================================================
# Script d'exécution de tests (run-tests.ps1) appelé par le job CI
# =============================================================================

$Config = New-PesterConfiguration

# 1. Spécification de l'emplacement des tests
$Config.Run.Path = ".\Tests\"

# 2. Activation de l'export XML au format NUnit (Standard CI/CD)
$Config.TestResult.Enabled      = $true
$Config.TestResult.OutputFormat = "NUnitXml"
$Config.TestResult.OutputPath   = ".\test-results.xml"

# 3. Forcer Pester à quitter le processus avec exit 1 si au moins un test échoue
$Config.Run.Exit = $true

# 4. Lancement de la campagne de tests
Invoke-Pester -Configuration $Config
```

Si un seul bloc `It` échoue, l'instruction `$Config.Run.Exit = $true` ordonne à PowerShell de quitter avec le code `exit 1`, stoppant immédiatement la progression du pipeline. L'orchestrateur lit ensuite le fichier `test-results.xml` pour afficher graphiquement la liste des assertions validées et le détail des erreurs.

## 5. Synthèse : Structure d'un Fichier Pipeline (`.gitlab-ci.yml`)

L'enchaînement de ces étapes est matérialisé par un fichier déclaratif placé à la racine du dépôt Git :

```yaml
# =============================================================================
# Définition de la Pipeline CI/CD (.gitlab-ci.yml)
# =============================================================================

stages:
  - lint
  - test
  - deploy
  - verify

# Étape 1 : Analyse Statique du code (Linter)
AnalyseSyntaxique:
  stage: lint
  script:
    - pwsh -Command "Invoke-ScriptAnalyzer -Path .\Src -EnableExit"

# Étape 2 : Tests Unitaires Pester (Isolation avec Mocks)
TestsUnitaires:
  stage: test
  script:
    - pwsh -File .\Scripts\run-tests.ps1
  artifacts:
    reports:
      junit: test-results.xml

# Étape 3 : Déploiement automatisé
DeploiementProduction:
  stage: deploy
  script:
    - pwsh -File .\Scripts\deploy.ps1
  environment:
    name: production

# Étape 4 : Tests d'intégration et audit de conformité réel
ValidationInfrastructure:
  stage: verify
  script:
    - pwsh -File .\Scripts\run-integration-tests.ps1
```

## 6. La Frise Chronologique du Pipeline DevOps (IaC)

```
[1. Planification] ──► [2. Code & Commit] ──► [3. Lint (Analyse Statique)]
                                                         │
                                                         ▼
[6. Verify (Integ.)] ◄── [5. Deploy (Prod)] ◄── [4. Test (Unitaires)]
```

1. **Planification :** Création d'un ticket décrivant le besoin (ouverture de flux, nouveau nœud de calcul, compte de service).
2. **Code & Commit :** L'ingénieur modifie le script, le module ou la configuration DSC sur son poste et soumet son *commit*.
3. **Lint (Pipeline) :** `PSScriptAnalyzer` vérifie l'absence d'alias, de mots de passe en clair et le respect de la nomenclature officielle.
4. **Test (Pipeline) :** `Pester` exécute les tests unitaires (avec Mocks) pour garantir l'intégrité de la logique interne sans toucher au matériel.
5. **Deploy (Pipeline) :** Le runner exécute la commande de déploiement réel (`Invoke-Command`, application d'un MOF DSC, etc.).
6. **Verify (Pipeline) :** Une série de tests d'intégration sans mock interroge le système de production pour valider que le service tourne et que le port TCP écoute réellement.
