# Sécurisation des Actions Destructrices avec -WhatIf et ShouldProcess

Ce document constitue le guide de référence sur la gestion du risque et la simulation d'actions d'administration sous PowerShell. Il détaille l'activation du mécanisme natif de simulation, l'implémentation de la méthode `$PSCmdlet.ShouldProcess()`, le rôle stratégique du bloc `process` face au pipeline, la hiérarchie des niveaux de confirmation (`ConfirmImpact`), la propagation des paramètres aux commandes imbriquées et les patrons de conception sécurisés.

## 1. La Gestion du Risque en Production

En administration système, la puissance d'automatisation de PowerShell présente un risque opérationnel symétrique :

* Une simple boucle ou un filtre pipeline mal formulé combiné à une action destructrice peut modifier, altérer ou supprimer des milliers d'éléments en quelques secondes.

* Une erreur sur un nom de serveur, une coquille dans un chemin de fichier ou un identifiant de processus erroné peut paralyser des services d'infrastructure critiques.

### 1.1 Mauvais script

Les administrateurs débutants tentent régulièrement d'introduire des commutateurs personnalisés pour vérifier leur algorithme :

**APPROCHE ARTISANALE PROSCRITE :**

```
param(
    [string]$Cible, 
    [bool]$Simulation = $true
)

if ($Simulation) {
    Write-Host "Simulation : suppression de $Cible"
} else {
    # Action destructive réelle
}

```

**Pourquoi ce modèle est interdit en entreprise ?**

* **Non-standardisé :** Chaque concepteur invente son propre nom (`-DryRun`, `-TestOnly`, `-Fake`, `-Simu`).

* **Incompatible avec l'écosystème :** Les ordonnanceurs d'entreprise, les plateformes CI/CD et les outils d'audit ne savent pas dialoguer avec des commutateurs inventés.

* **Absence de cascade :** Les cmdlets natives appelées à l'intérieur du script ignorent cette simulation et s'exécutent réellement si le codeur oublie une seule condition.

### 1.2 Le standard industriel : -WhatIf et SupportsShouldProcess

PowerShell intègre un mécanisme officiel et universel : le protocole `SupportsShouldProcess`. Lorsqu'une fonction déclare ce standard :

* Le moteur lui injecte automatiquement deux paramètres universels : `-WhatIf` et `-Confirm`.

* La fonction délègue au moteur PowerShell la responsabilité d'intercepter ou d'exécuter l'action physique.

* L'état de simulation se propage nativement aux commandes système sous-jacentes.

## 2. L'Architecture sous le Capot : SupportsShouldProcess et \$PSCmdlet

Pour doter un script ou une fonction de cette capacité, deux prérequis indissociables doivent figurer dans le code :

```
[Attribut CmdletBinding] SupportsShouldProcess = $true
 │
 ├─► Injection automatique par le moteur de : -WhatIf et -Confirm
 │
 ▼
[Méthode d'Interception du Moteur] $PSCmdlet.ShouldProcess($Cible, $Operation)
 │
 ├── Exécution standard ──► Renvoie $true  ──► L'action physique s'exécute
 ├── Avec -WhatIf       ──► Affiche l'action, renvoie $false ──► Action neutralisée
 └── Avec -Confirm      ──► Ouvre l'invite interactive (O/N) ──► Dépend du choix opérateur

```

### 2.1 Déclaration dans l'en-tête

La prise en charge s'active dans l'attribut `[CmdletBinding()]` placé au sommet du bloc de paramètres :

```
[CmdletBinding(SupportsShouldProcess = $true)] 
param(
    [Parameter(Mandatory = $true)]
    [string]$NomElement 
)

```

Dès cette ligne présente, les paramètres `-WhatIf` et `-Confirm` deviennent actifs, visibles dans l'aide (`Get-Help`) et auto-complétés via la touche TAB.

### 2.2 La méthode maîtresse : \$PSCmdlet.ShouldProcess()

L'attribut en en-tête informe le système que la fonction sait simuler, mais il n'interrompt rien de lui-même : l'administrateur doit obligatoirement conditionner chaque action destructrice avec la méthode `$PSCmdlet.ShouldProcess()` :

```
if ($PSCmdlet.ShouldProcess($Cible, $Action)) {
    # Ce bloc ne s'exécute QUE si ShouldProcess renvoie $true.
    # En présence de -WhatIf, le moteur renvoie $false : le bloc est ignoré.
}

```

## 3. Le Rôle Fondamental du Bloc `process` dans les Fonctions Avancées

Dès lors qu'un script ou une fonction avancée doit interagir avec le pipeline ou exécuter des actions répétitives sécurisées, la maîtrise du bloc `process` devient indispensable.

### 3.1 Le cycle de vie à trois phases : begin, process, end

Dans une fonction avancée, le corps d'exécution peut être structuré en trois blocs distincts régis par le moteur PowerShell :

```
Flux d'objets entrants via le Pipeline (|)
 │
 ▼
 ┌─────────────────────────────────────────────────────────────────┐
 │ begin { ... } ──► Exécuté 1 seule fois à l'initialisation       │
 └─────────────────────────────────────────────────────────────────┘
 │
 ▼
 ┌─────────────────────────────────────────────────────────────────┐
 │ process { ... } ──► EXÉCUTÉ POUR CHAQUE OBJET DU PIPELINE       │
 │                     (Itération unitaire dynamique)              │
 └─────────────────────────────────────────────────────────────────┘
 │
 ▼
 ┌─────────────────────────────────────────────────────────────────┐
 │ end { ... } ──► Exécuté 1 seule fois à la clôture               │
 └─────────────────────────────────────────────────────────────────┘

```

* **`begin { ... }` :** S'exécute une seule fois avant que le premier objet n'arrive du pipeline. Idéal pour initialiser des compteurs, ouvrir une connexion ou charger des dictionnaires de référence.

* **`process { ... }` :** C'est le cœur battant du pipeline. Si $N$ objets traversent le tube, le bloc `process` s'exécute $N$ fois consécutives, l'objet courant étant accessible via la variable automatique `$_` (ou le paramètre lié).

* **`end { ... }` :** S'exécute une seule fois après que la totalité des objets a été traitée. Permet d'émettre des synthèses, d'écrire des récapitulatifs ou de fermer des sockets.

### 3.2 Pourquoi et quand utiliser process ?

| Contexte d'appel | Sans bloc `process` (Code brut) | Avec bloc `process` explicite | 
| ----- | ----- | ----- | 
| **Appel direct par argument**  `Commande -Param $Valeur` | Le code s'exécute une seule fois sur la valeur transmise. | Le bloc `process` s'exécute exactement une fois. Résultat identique. | 
| **Appel via le Pipeline**  \`\$Objets | Commande\` | **Échec partiel :** Le code ne s'exécute qu'une seule fois, en ne traitant que le *tout dernier* objet de la collection. | 

### 3.3 L'articulation entre process et ShouldProcess()

Lorsque vous concevez un outil destructeur compatible pipeline (ex : suppression de ressources injectées depuis un fichier ou un audit), `$PSCmdlet.ShouldProcess()` doit obligatoirement être invoqué au sein du bloc `process`.
Ainsi, le moteur PowerShell consulte l'opérateur ou affiche la simulation *individuellement* pour chaque élément :

```
function Remove-CustomItem { 
    [CmdletBinding(SupportsShouldProcess = $true)] 
    param(
        [Parameter(ValueFromPipeline = $true)]
        [string]$Identifiant 
    )

    process {
        # Evalué unitairement à chaque passage d'objet 
        if ($PSCmdlet.ShouldProcess("Élément [$Identifiant]", "Supprimer définitivement")) {
            # Action réelle appliquée à l'élément courant $_
        } 
    } 
}

```

## 4. Patrons d'Implémentation et Micro-Snippets de Référence

Afin de ne pas dépendre d'un code métier complet, voici le squelette syntaxique minimal universel pour sécuriser une action unitaire.

### 4.1 La signature à deux arguments : Cible et Verbe

Pour que les messages d'avertissement du système soient exploitables par les outils de supervision, l'administrateur transmet toujours deux chaînes explicites à la méthode :

* **La Cible :** L'élément exact impacté (nom de la ressource, identifiant système, chemin).

* **L'Action / Verbe :** La nature précise de l'opération et son impact.

**Micro-snippet : Structure élémentaire d'interception**

```
$Cible = "Serveur-01 / Disque F:" 
$Action = "Démontage du volume et purge des descripteurs"

if ($PSCmdlet.ShouldProcess($Cible, $Action)) {
    # Exécution de l'ordre destructeur
}

```

### 4.2 Les trois comportements d'exécution

1. **Mode Nominal (Direct) :** `Ma-Commande -Cible "ObjetA"`
   `$PSCmdlet.ShouldProcess()` évalue les seuils, renvoie `$true` sans rien afficher. L'action est immédiatement exécutée.

2. **Mode Simulation (`-WhatIf`) :** `Ma-Commande -Cible "ObjetA" -WhatIf`
   Le moteur intercepte la demande, affiche automatiquement le message normé à l'écran et renvoie `$false` :
   `What if: Performing the operation "Démontage du volume..." on target "Serveur-01 / Disque F:".`
   Le bloc d'action physique est neutralisé.

3. **Mode Interactif (`-Confirm`) :** `Ma-Commande -Cible "ObjetA" -Confirm`
   Le moteur suspend l'exécution et affiche l'invite de dialogue console :

   ```
   Confirm
   Are you sure you want to perform this action?
   Performing the operation "Démontage du volume..." on target "Serveur-01 / Disque F:". 
   [Y] Yes  [A] Yes to All  [N] No  [L] No to All  [S] Suspend  [?] Help (default is "Y"):
   
   ```

   Le renvoi de `$true` ou `$false` dépend strictement du choix saisi par l'opérateur.

## 5. Les Deux Cas Fréquents d'Architecture

### Les effets de bord cosmétiques hors condition

L'erreur d'architecture la plus fréquente en entreprise consiste à placer l'appel destructeur sous la condition, mais à inscrire le message de réussite ou l'écriture dans le journal de bord *après* le bloc conditionnel :

**PIÈGE ARCHITECTURAL (FAUX POSITIF DE LOGS) :**

```
if ($PSCmdlet.ShouldProcess($Cible, "Suppression")) {
    # Action physique
}

# ERREUR : Ces lignes s'exécutent même si l'administrateur a passé -WhatIf ! 
Write-Host "Opération validée avec succès sur $Cible." -ForegroundColor Green 
Add-Content -Path "C:\Audit\operations.log" -Value "[$Cible] Détruit avec succès."

```

**Règle d'étanchéité :** Tout affichage de succès, toute mise à jour de compteur ou toute écriture dans un fichier journal doit résider **strictement à l'intérieur** du bloc conditionné par `ShouldProcess()`.

**ARCHITECTURE CONFORME ET ÉTANCHE :**

```
if ($PSCmdlet.ShouldProcess($Cible, "Suppression")) {
    # 1. Action physique réelle
    # 2. Journalisation du succès réel uniquement
}
else {
    # Branche optionnelle : trace verbeuse de neutralisation
    Write-Verbose "Simulation active ou refus opérateur pour : $Cible" 
}

```

### Le double dialogue d'avertissement (Double Prompt)

Si votre fonction appelle une commande interne qui intègre elle-même sa propre sécurité (comme `Stop-Process`, `Remove-Item` ou `Stop-Service`), l'opérateur qui exécute votre script avec `-Confirm` subira deux demandes de validation successives pour une seule tâche :

1. L'invite déclenchée par votre script parent.

2. L'invite déclenchée par la sous-commande native.

**Bonne pratique :**

```
if ($PSCmdlet.ShouldProcess($Cible, "Arrêt")) {
    # On force la commande interne à obéir à l'accord déjà donné
    Stop-Process -Id $PID -Force -Confirm:$false
}

```

En appliquant explicitement `-Confirm:$false` sur la commande interne, vous garantissez qu'elle ne redemandera rien à l'opérateur une fois l'accord parent validé.

## 6. Niveaux de Criticité : ConfirmImpact et \$ConfirmPreference

Pourquoi certaines actions Windows demandent-elles confirmation spontanément sans même avoir tapé `-Confirm` ? La réponse réside dans la balance des seuils de criticité.

### 6.1 Les niveaux d'impact (ConfirmImpact)

Lors de la déclaration de l'en-tête, le développeur évalue le degré de dangerosité de son traitement via l'attribut `ConfirmImpact` :

| Niveau déclaré | Degré de danger | Cas d'usage type | 
| ----- | ----- | ----- | 
| **`Low`** | Risque mineur | Écriture de traces, modification de propriétés non bloquantes. | 
| **`Medium`** (défaut) | Risque standard | Suppression de fichiers isolés, arrêt d'un processus utilisateur. | 
| **`High`** | Danger critique | Formatage de disque, arrêt d'un serveur, destruction d'un service vital. | 

### 6.2 L'équation arithmétique de seuil

PowerShell compare en temps réel le niveau de risque déclaré par la commande face à la variable de tolérance de la session active (`$ConfirmPreference`, qui vaut `High` par défaut sous Windows) :

* **Si `ConfirmImpact = 'Medium'` et `$ConfirmPreference = 'High'` :**
  Exécution directe sans solliciter l'administrateur.

* **Si `ConfirmImpact = 'High'` et `$ConfirmPreference = 'High'` :**
  PowerShell interrompt l'exécution et affiche l'invite interactive, *même si l'administrateur n'a jamais tapé `-Confirm`*.

**Déclaration d'une commande à haut risque opérationnel :**

```
[CmdletBinding(SupportsShouldProcess = $true, ConfirmImpact = 'High')] 
param(
    [string]$CibleCritique
)

```

### 6.3 Automatisation nocturne sans blocage

Dans une tâche planifiée ou un pipeline CI/CD automatisé la nuit, aucune présence humaine n'est disponible pour taper `Y` sur une commande classée en `High`.
Pour forcer l'exécution automatique sans bloquer le script, l'ordonnanceur neutralise l'interactivité via la syntaxe :

```
Ma-CommandeCritique -Cible "Cluster-Node" -Confirm:$false

```

## 7. Détecter l'État de Simulation dans le Code (\$WhatIfPreference)

Dans certains scénarios, le script a besoin de savoir si le mode simulation a été sollicité en amont (par exemple pour modifier une requête de diagnostic préalable ou enrichir l'objet de restitution final).

Lorsque `-WhatIf` est fourni en argument, le moteur PowerShell assigne automatiquement la valeur `$true` à la variable de portée locale : `$WhatIfPreference`.

**Micro-snippet de détection :**

```
# Détection de l'état d'exécution
$EstEnSimulation = [bool]$WhatIfPreference

# Exploitation pour un objet bilan final
[PSCustomObject]@{ 
    CiblesTraitees = $Compteur 
    ModeSimulation = $EstEnSimulation 
}

```

## 8. Synthèse des Bonnes Pratiques d'Architecture

* **Bannir les commutateurs artisanaux :** Ne jamais inventer de paramètres `-Test` ou `-DryRun`. Utiliser exclusivement `SupportsShouldProcess = $true`.

* **Exploiter le bloc `process` :** Encapsuler systématiquement les actions unitaires dans un bloc `process` dès lors que des objets peuvent transiter via le pipeline.

* **Cibler chirurgicalement l'action destructive :** Aucune commande de modification ne doit être exécutée en dehors d'une garde `if ($PSCmdlet.ShouldProcess())`.

* **Isoler strictement la journalisation :** Ne jamais consigner d'action réussie si `ShouldProcess()` a renvoyé `$false`.

* **Neutraliser les doubles invites :** Passer systématiquement `-Confirm:$false` aux cmdlets natives destructrices imbriquées sous la garde parente.

* **Calibrer ConfirmImpact avec discernement :** Réserver la valeur `'High'` uniquement aux actions irréversibles mettant en péril la continuité de service.
