# **Analyse Statique avec PSScriptAnalyzer**

## **Objectif**

Mettre en pratique le concept de **"Shift-Left"**. Vous allez auditer un script fonctionnel mais truffé de mauvaises pratiques historiques, analyser le rapport du Linter, et appliquer la remédiation pour atteindre le standard "Zéro Défaut" exigé par une chaîne CI/CD.

---

## **Exercice 1 : Préparation du script "Sale" (The Dirty Script)**

1. Dans votre dossier `C:\Audit\`, créez un nouveau fichier nommé `Check-Systeme.ps1`.  
2. Copiez-collez exactement le code suivant (avec ses défauts) et sauvegardez le fichier :

```powershell
function Check-Systeme {
    param(
        $Serveur = "localhost"
    )

    $MotDePasseAdmin = "P@ssw0rd_2026!"
    
    Write-Host "Lancement de l'audit sur $Serveur..." -ForegroundColor Yellow

    # Récupération des services
    $services = gwmi Win32_Service -ComputerName $Serveur
    
    # Filtrage des services en cours d'exécution
    $actifs = $services | ? { $_.State -eq 'Running' }
    
    echo "Nombre de services actifs : $($actifs.Count)"
}
```

&nbsp;

> **Remarque :** Si vous lancez ce script, il fonctionne. C'est tout le piège de l'administration classique : le code s'exécute, donc l'administrateur pense qu'il est valide.

## **Exercice 2 : L'Audit Impitoyable**

Vous allez maintenant endosser le rôle du pipeline d'intégration continue.

1. Dans votre console PowerShell, lancez l'audit statique sur votre fichier :

```powershell
Invoke-ScriptAnalyzer -Path "C:\Audit\Check-Systeme.ps1"
```

&nbsp;

2. **Analyse du rapport :**  
   * Combien de violations (lignes) le moteur vous remonte-t-il ?  
   * Repérez la violation de sévérité **Error** concernant la sécurité. Quelle est la règle déclenchée ?  
   * Repérez les violations concernant la syntaxe (`gwmi`, `?`, `echo`). Quelle est la règle déclenchée ?  
   * Quelle règle reproche au script le nom même de sa fonction ?

## **Exercice 3 : La Remédiation (Refactoring)**

Votre objectif est de corriger le fichier `Check-Systeme.ps1` pour que `Invoke-ScriptAnalyzer` ne renvoie plus **aucune ligne**.

### **Aide pour la remédiation :**

1. **Nom de la fonction :** Remplacez le verbe `Check` par un verbe approuvé (ex : `Test` ou `Get`).  
2. **Mot de passe :** Supprimez cette variable en texte brut (en production, on utiliserait un paramètre `[PSCredential]` ou le module `SecretManagement`).  
3. **Write-Host :** Remplacez-le par `Write-Verbose` ou `Write-Information`.  
4. **Les Alias :**  
   * Remplacez `gwmi` par `Get-WmiObject` (ou idéalement par `Get-CimInstance`).  
   * Remplacez `?` par `Where-Object`.  
   * Remplacez `echo` par `Write-Output`.

### **Validation :**

Relancez l'analyse statique :

```powershell
Invoke-ScriptAnalyzer -Path "C:\Audit\Check-Systeme.ps1"
```

&nbsp;

Le silence de la console (aucun retour) est la preuve que votre code est certifié pour la production.

## **Exercice 4 (Bonus DevOps) : Le Fichier de Tolérance**

Parfois, pour de petits scripts d'interface console, l'usage de `Write-Host` est assumé pour de l'affichage coloré, et l'on ne souhaite pas bloquer la chaîne CI/CD pour cette règle spécifique.

1. Créez un fichier de paramètres nommé `C:\Audit\LinterSettings.psd1` avec le contenu suivant :

```powershell
@{
    IncludeDefaultRules = $true
    ExcludeRules        = @(
        'PSAvoidUsingWriteHost'
    )
}
```

&nbsp;

2. Réintroduisez volontairement un `Write-Host` dans votre script PowerShell.  
3. Lancez l'analyse en appliquant votre fichier de configuration :

```powershell
Invoke-ScriptAnalyzer -Path "C:\Audit\Check-Systeme.ps1" -Settings "C:\Audit\LinterSettings.psd1"
```

&nbsp;

> **Constat :** L'analyseur valide votre code car vous avez formellement documenté et déclaré cette exception technique dans le projet.
