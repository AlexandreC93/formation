# Parallélisme, Multithreading et Jobs d'Arrière-Plan en PowerShell

Ce document détaille les mécanismes d'exécution asynchrone et concurrente, le fonctionnement du multithreading moderne, le cycle de vie complet des tâches de fond (*Background Jobs*), ainsi que les règles d'optimisation indispensables pour diviser le temps de traitement des scripts d'infrastructure.

---

## 1. Paralléliser en Administration Système

### 1.1 La limite structurelle du modèle séquentiel

Par défaut, l'interpréteur PowerShell est **synchrone** et **mono-thread** : chaque commande s'exécute l'une après l'autre sur le thread principal de la console.

Dans une boucle séquentielle classique :
* Si une tâche unitaire prend **2 secondes** (par exemple une vérification de port TCP ou un ping réseau avec temporisation),
* Et que vous devez auditer un parc de **30 serveurs**,
* L'exécution globale nécessite : $30 \times 2\text{ s} = 60\text{ secondes}$.

Pendant toute cette minute, la console PowerShell de l'administrateur est **totalement gelée** : impossible de saisir une autre commande, d'afficher un retour visuel réactif en temps réel ou d'interrompre proprement une tâche bloquée sans tuer le processus hôte.

### 1.2 Le paradigme asynchrone et concurrent

En exécution concurrente, PowerShell distribue les opérations sur plusieurs unités d'exécution simultanées (cœurs de processeur ou threads du système d'exploitation).

Pour nos 30 serveurs exécutés en parallèle avec un délai unitaire de 2 secondes, le temps global de traitement passe d'une minute entière à **environ 3 à 4 secondes** (temps de latence réseau + marge d'initialisation).

## 2. Mesure Objective des Performances (`Measure-Command`)

Avant de chercher à optimiser un traitement, l'administrateur doit mesurer rigoureusement son temps d'exécution initial afin de quantifier le retour sur investissement.

La cmdlet `Measure-Command` exécute un bloc de script `{}` en isolant précisément sa durée d'exécution, sans polluer l'affichage console avec les objets produits.

```powershell
# Chronométrage d'un traitement séquentiel
$Chrono = Measure-Command {
    1..5 | ForEach-Object {
        Start-Sleep -Seconds 1
    }
}

# Extraction du temps d'exécution en secondes
$Chrono.TotalSeconds
```

### Propriétés clés de l'objet `[TimeSpan]` renvoyé :
* **`TotalSeconds`** : Durée totale convertie en secondes (nombre décimal haute précision).
* **`TotalMilliseconds`** : Durée en millisecondes (indispensable pour les micro-benchmarks).
* **`Minutes` / `Seconds`** : Décomposition calendaire de la durée.

## 3. Le Multithreading Moderne : `ForEach-Object -Parallel` (PowerShell 7+)

Introduite avec PowerShell 7, cette syntaxe permet d'exécuter des itérations simultanées **au sein du même processus hôte**, via des threads managés .NET légers.

### 3.1 Fonctionnement interne et mécanisme de Thread Pool

Contrairement au modèle classique séquentiel qui traite les éléments du pipeline un à un, `ForEach-Object -Parallel` injecte chaque élément dans le pool de threads (*ThreadPool*) du processus `pwsh.exe` :

```powershell
$Serveurs = @("SRV-APP01", "SRV-APP02", "SRV-APP03", "SRV-APP04", "SRV-APP05")

$Serveurs | ForEach-Object -ThrottleLimit 5 -Parallel {
    $ThreadId = [System.Threading.Thread]::CurrentThread.ManagedThreadId
    Write-Host "[$_] Audit en cours sur le Thread ID : $ThreadId" -ForegroundColor Cyan
    Start-Sleep -Seconds 2
}
```

#### Exemple de calcul local parallèle (CPU-Bound) :
Le processeur local utilise plusieurs cœurs pour hacher 4 gros fichiers ISO en même temps :

```powershell
Get-ChildItem "C:\ISOs\*.iso" | ForEach-Object -Parallel {
    Get-FileHash -Path $_.FullName -Algorithm SHA256
}
```

*(À ne pas confondre avec `Invoke-Command`, où le calcul est déporté sur le processeur distant de chaque serveur cible).*

### 3.2 Injection de variables parentes : Le modificateur de portée `$using:`

Puisque chaque thread s'exécute dans un *Runspace* isolé, les variables déclarées dans le script principal ne sont pas implicitement accessibles dans le bloc d'instructions parallèles.

Pour importer la valeur d'une variable locale dans le bloc d'exécution, on utilise le préfixe de portée **`$using:`** :

```powershell
$SeuilAlerteMo = 500

Get-Content "C:\Audit\serveurs.txt" | ForEach-Object -Parallel {
    # $SeuilAlerteMo n'existe pas ici sans le préfixe $using:
    $Limite = $using:SeuilAlerteMo

    Get-Process | Where-Object WorkingSet64 -gt ($Limite * 1MB)
}
```

### 3.3 Exécution non-bloquante avec le commutateur `-AsJob`

Par défaut, `ForEach-Object -Parallel` libère plusieurs threads mais **bloque la console** jusqu'à ce que le dernier élément de la collection soit traité.

Pour rendre l'opération entièrement asynchrone et récupérer immédiatement la main dans le shell, on ajoute le commutateur **`-AsJob`** :

```powershell
# Démarre l'exécution multithreadée en tâche de fond
$MonJobMultiThread = 1..20 | ForEach-Object -Parallel {
    Start-Sleep -Seconds 2
    $_ * 10
} -AsJob

# La console est immédiatement disponible. On récupère les résultats à la demande :
$MonJobMultiThread | Receive-Job -Wait -AutoRemoveJob
```

### 3.4 Analyse technique : `ForEach-Object -Parallel`

| Caractéristique | Analyse technique |
| :--- | :--- |
| **Avantages** | **1. Empreinte mémoire minime :** Chaque thread ne consomme qu'environ ~1 Mo à 2 Mo de RAM.<br>**2. Latence de démarrage quasi-nulle :** Démarrage instantané ($< 50\text{ ms}$).<br>**3. Syntaxe concise :** Aucun cycle de vie lourd à orchestrer manuellement.<br>**4. Pipeline fluide :** Les objets retournés sortent directement dans le flux standard sans désérialisation complexe.<br>**5. Régulation native :** Contrôle précis de la concurrence via `-ThrottleLimit`. |
| **Inconvénients** | **1. Dépendance de version :** Strictement réservé à **PowerShell 7+** (absent de Windows PowerShell 5.1 natif).<br>**2. Risque de concurrence (*Thread Safety*) :** Si plusieurs threads écrivent simultanément dans une ressource partagée sans verrouillage (*Mutex* / *Lock*), les données risquent d'être corrompues.<br>**3. Débogage plus complexe :** La capture et l'isolation des erreurs au sein de 20 threads concurrents impose une gestion rigoureuse des blocs `try / catch`. |

## 4. Les Tâches d'Arrière-Plan Multi-Processus : Background Jobs (`Start-Job`)

Les **Background Jobs** représentent la technologie historique de traitement asynchrone de PowerShell, disponible de façon universelle sur toutes les versions du système (Windows PowerShell 2.0 à 5.1 et PowerShell 7+).

### 4.1 Fonctionnement interne : L'isolation par processus Windows

Contrairement au multithreading, un Job lancé via `Start-Job` ne crée pas un simple thread : **il instancie un processus système Windows complet et autonome (`powershell.exe`) en arrière-plan**.

```text
[SESSION PRINCIPALE (powershell.exe)] ── (Console interactive active)
 │
 ├── Start-Job ──► [Processus Enfant 1 : powershell.exe] (~35 Mo RAM)
 ├── Start-Job ──► [Processus Enfant 2 : powershell.exe] (~35 Mo RAM)
 └── Start-Job ──► [Processus Enfant 3 : powershell.exe] (~35 Mo RAM)
```

Chaque sous-processus charge son propre moteur .NET, ses propres modules et sa propre allocation mémoire.

### 4.2 Le cycle de vie rigoureux d'un Job

Le pilotage d'un Job repose sur **5 étapes séquentielles indispensables** :

```text
[Start-Job]
 │
 ▼ État : Running   ◄─── (Surveillance continue : Get-Job)
 │
 ▼
[Wait-Job]         ◄─── (Attente de terminaison globale ou avec Timeout)
 │
 ▼ État : Completed
 │
 ▼
[Receive-Job]      ◄─── (Rapatriement des données en session principale)
 │
 ▼
[Remove-Job]       ◄─── (Purge obligatoire de la mémoire vive)
```

#### Étape 1 : Démarrer la tâche (`Start-Job`)

```powershell
$MonJob = Start-Job -Name "ScanStockage" -ScriptBlock {
    param($Lecteur)
    Start-Sleep -Seconds 3
    Get-CimInstance -ClassName Win32_LogicalDisk -Filter "DeviceID='$Lecteur:'"
} -ArgumentList "C"
```

> **Le piège du passage d'arguments :** Le sous-processus ne partage aucune mémoire avec votre console. Le scope `$using:` n'est pas supporté par `Start-Job` sous Windows PowerShell 5.1. Il faut obligatoirement transmettre les variables via **`-ArgumentList`** et les réceptionner avec **`param()`** au début du `ScriptBlock`.

#### Étape 2 : Surveiller l'état d'avancement (`Get-Job`)

Permet de relever l'`Id`, le `Name` et l'état (`State`) de la tâche :
* **`NotStarted`** : En file d'attente d'instanciation.
* **`Running`** : En cours d'exécution active sur le processeur.
* **`Completed`** : Terminé avec succès ; des objets attendent dans le tampon.
* **`Failed`** : Une erreur bloquante non interceptée a fait planter le code du Job.
* **`Stopped`** : Tâche interrompue prématurément par un opérateur (`Stop-Job`).

```powershell
# Compter le nombre de jobs encore en activité
(Get-Job -State Running).Count
```

#### Étape 3 : Synchroniser et bloquer (`Wait-Job`)

Si la suite du script a besoin des résultats pour consolider un rapport :

```powershell
# Attendre la fin de tous les jobs de la collection
$MesJobs | Wait-Job

# Attendre avec un délai maximum (Timeout de 15 secondes)
Wait-Job -Name "ScanStockage" -Timeout 15
```

#### Étape 4 : Récolter les données et le piège du tampon (`Receive-Job`)

```powershell
$Resultats = Receive-Job -Name "ScanStockage"
```

> **Attention au piège de la consommation du buffer :** Par défaut, `Receive-Job` agit comme une vidange de file d'attente (*Queue*). Dès que les données sont lues, le tampon mémoire du Job est **définitivement effacé**. Un second appel à `Receive-Job` renverra `$null`.  
> Pour autoriser des lectures multiples sans vider la mémoire tampon, ajoutez impérativement le paramètre **`-Keep`** :

```powershell
Receive-Job -Name "ScanStockage" -Keep
```

#### Étape 5 : Nettoyer obligatoirement la mémoire (`Remove-Job`)

Contrairement à une variable classique nettoyée automatiquement par le ramasse-miettes (*Garbage Collector*), les jobs terminés **restent stockés indéfiniment en mémoire RAM** tant que la console PowerShell reste ouverte.

Dans un script d'audit régulier ou un traitement portant sur plusieurs dizaines de cibles, l'absence de purge génère une **fuite de mémoire majeure** (*Memory Leak*) :

```powershell
# Règle de nettoyage systématique en fin de script :
Get-Job -State Completed, Failed, Stopped | Remove-Job
```

### 4.3 Analyse technique : `Start-Job`

| Caractéristique | Analyse technique |
| :--- | :--- |
| **Avantages** | **1. Compatibilité universelle :** Fonctionne nativement sur 100 % des machines Windows (PowerShell 2.0 à 7+).<br>**2. Asynchronie totale immédiate :** Rend instantanément la main à la console interactive.<br>**3. Cloisonnement absolu :** En cas d'effondrement mémoire ou de crash critique dans le job, la console hôte ne plante jamais.<br>**4. Sécurité des variables :** Aucun risque de corruption mémoire entre les tâches (espaces d'adressage distincts). |
| **Inconvénients** | **1. Empreinte mémoire massive :** Compter environ ~35 Mo de RAM par tâche (soit 700 Mo à 1 Go pour seulement 20-30 jobs).<br>**2. Latence d'initialisation élevée :** Compter 1 à 2 secondes rien que pour instancier le sous-processus.<br>**3. Désérialisation des objets (CLIXML) :** Les méthodes actives sur les objets rapatriés sont coupées.<br>**4. Lourdeur opérationnelle :** Obligation de gérer tout le cycle de récolte et de purge sous peine de fuite mémoire. |

## 5. Comparatif Architectural Approfondi : Processus vs Threads

Pour concevoir des outils d'infrastructure professionnels, il est impératif de comprendre ce qui se passe physiquement au niveau du système d'exploitation :

```text
[1. ARCHITECTURE START-JOB : MULTI-PROCESSUS]
Processus Principal (powershell.exe)
├── Sous-processus 1 (powershell.exe) ──► ~35 Mo RAM / 1.5s démarrage
├── Sous-processus 2 (powershell.exe) ──► ~35 Mo RAM / 1.5s démarrage
└── Sous-processus 3 (powershell.exe) ──► ~35 Mo RAM / 1.5s démarrage
Total pour 20 jobs = ~700 Mo à 1 Go de RAM et pic CPU à l'initialisation.

[2. ARCHITECTURE FOREACH-OBJECT -PARALLEL : MULTI-THREAD]
Processus Unique (pwsh.exe)
├── Thread 1 (Tâche A) ──► ~1 Mo RAM / Démarrage quasi-instantané
├── Thread 2 (Tâche B) ──► ~1 Mo RAM / Démarrage quasi-instantané
└── Thread 3 (Tâche C) ──► ~1 Mo RAM / Démarrage quasi-instantané
Total pour 20 threads = ~20 Mo de RAM supplémentaires seulement.
```

### Synthèse comparative

| Critère d'évaluation | Jobs classiques (`Start-Job`) | Multithreading natif (`ForEach-Object -Parallel`) |
| :--- | :--- | :--- |
| **Technologie système** | Processus Windows indépendant (`powershell.exe`) | Threads managés .NET dans le processus hôte |
| **Compatibilité système** | **Universelle** (PowerShell 2.0 à 7+) | **PowerShell 7+ uniquement** (ou module externe `ThreadJob` en 5.1) |
| **Consommation RAM** | **Lourde** (~35 Mo par tâche) | **Minime** (~1 à 2 Mo par thread) |
| **Latence au lancement** | Lente (1 à 2 secondes par tâche) | Instantanée ($< 50\text{ ms}$) |
| **Passage de données** | `-ArgumentList` et bloc `param()` obligatoire | Modificateur de scope `$using:NomVariable` |
| **Plafond d'extensibilité** | Restreint (10 à 30 jobs simultanés recommandés) | Très élevé (centaines de threads simultanés) |
| **Nature des objets** | Objets désérialisés (`Deserialized.*`) | Vrais objets .NET vivants en mémoire |

## 6. Régulation de la Charge : La Règle du `ThrottleLimit`

Lancer des opérations concurrentes sans restriction présente un risque critique : **l'effondrement des ressources de la machine hôte** (saturation CPU, épuisement de la mémoire ou engorgement de la carte réseau).

### 6.1 Le principe du pool glissant (*Worker Pool*)

Le paramètre **`-ThrottleLimit`** définit le nombre maximum de traitements simultanés autorisés à tourner en même temps :

```powershell
1..50 | ForEach-Object -ThrottleLimit 5 -Parallel {
    $Id = [System.Threading.Thread]::CurrentThread.ManagedThreadId
    Write-Host "Traitement du composant $_ sur le Thread $Id"
    Start-Sleep -Seconds 1
}
```

* **Comportement du moteur :** PowerShell démarre les 5 premières tâches. Dès que l'une d'entre elles s'achève, la 6ème démarre immédiatement dans le thread libéré. Le nombre de tâches concurrentes sur le système ne dépasse jamais le seuil fixé.

### 6.2 Comment dimensionner son `ThrottleLimit` ?

Le réglage optimal dépend de la nature des opérations exécutées :

* **Traitements orientés réseau ou attentes (I/O-Bound) :**  
  *(Exemples : ping de serveurs, requêtes API web REST, interrogation CIM distante, scan de ports).*  
  Le processeur passe la majeure partie de son temps en attente des paquets réseau. Vous pouvez fixer un seuil de concurrence élevé :
  $$\text{ThrottleLimit} = 20\text{ à }50$$

* **Traitements orientés calcul processeur (CPU-Bound) :**  
  *(Exemples : calculs de hachage SHA-256 de gros fichiers, compression d'archives, chiffrement).*  
  Au-delà du nombre de cœurs physiques, les threads se disputent le temps de calcul (*context switching*) et ralentissent le traitement global :
  $$\text{ThrottleLimit} = \text{Nombre de cœurs logiques (vCPU)}$$

## 7. Le Patron d'Architecture Industriel "Scatter-Gather" (Émettre - Récolter)

En production, l'architecture d'un script parallèle robuste repose sur le patron de conception **Scatter-Gather** (*Éparpiller pour exécuter, Rassembler pour synthétiser*) :

```text
[Phase 1 : ÉMISSION (Scatter)]
Lancement des tâches non-bloquantes (Start-Job ou ForEach-Object -Parallel -AsJob)
 │
 ▼
[Phase 2 : SURVEILLANCE (Monitor)]
Boucle de contrôle active avec retour visuel (Write-Progress)
 │
 ▼
[Phase 3 : RÉCOLTE (Gather)]
Rapatriement consolidé de l'ensemble des flux d'objets (Receive-Job)
 │
 ▼
[Phase 4 : PURGE (Sanitize)]
Destruction systématique des résidus mémoire dans un bloc finally (Remove-Job)
```

### Exemple de structure industrielle résiliente :

```powershell
$Serveurs = @("SRV-01", "SRV-02", "SRV-03", "SRV-04")
$Jobs = @()

try {
    # 1. Émission (Scatter)
    foreach ($Srv in $Serveurs) {
        $Jobs += Start-Job -Name "Audit_$Srv" -ScriptBlock {
            param($Nom)
            Start-Sleep -Seconds 2
            [PSCustomObject]@{
                Serveur = $Nom
                Statut  = "EnLigne"
                Date    = (Get-Date)
            }
        } -ArgumentList $Srv
    }

    # 2. Surveillance dynamique (Monitor)
    while (($Jobs | Where-Object State -eq 'Running').Count -gt 0) {
        $Termines = ($Jobs | Where-Object State -ne 'Running').Count
        $Pct = [math]::Round(($Termines / $Jobs.Count) * 100)
        Write-Progress -Activity "Audit Parallèle" -Status "$Termines / $($Jobs.Count) achevés" -PercentComplete $Pct
        Start-Sleep -Milliseconds 500
    }

    # 3. Récolte (Gather)
    $Rapport = $Jobs | Receive-Job
    $Rapport | Format-Table -AutoSize
}
finally {
    # 4. Purge systématique garantie même en cas d'erreur ou Ctrl+C (Sanitize)
    Write-Progress -Activity "Audit Parallèle" -Completed
    $Jobs | Remove-Job -Force
}
```

## 8. Synthèse des Bonnes Pratiques de Production

1. **Toujours chronométrer pour vérifier le gain réel :** Lancer un job pour une action qui prend 5 ms est contre-productif, car le coût d'initialisation du sous-processus (1 à 2 secondes) dépasse largement le temps de traitement de l'action.
2. **Ne jamais laisser de Jobs orphelins :** Tout script qui manipule des jobs doit systématiquement appeler `Remove-Job` au sein d'un bloc de clôture `finally`.
3. **Utiliser `-Keep` pendant le développement :** En phase de test dans la console, ajoutez toujours le paramètre `-Keep` à `Receive-Job` pour éviter de purger accidentellement vos données de test lors d'une première lecture.
4. **Adapter l'outil à la version de PowerShell en production :**
   * **Sous PowerShell 7+ :** Privilégier systématiquement `ForEach-Object -Parallel` associé à `-ThrottleLimit` (ou avec `-AsJob` pour le non-bloquant).
   * **Sous Windows PowerShell 5.1 :** Utiliser `Start-Job` avec passage d'arguments strict via `-ArgumentList`, ou installer le module officiel Microsoft `ThreadJob` (`Start-ThreadJob`) pour bénéficier du multithreading léger en 5.1.
