# Architecture et Bonnes Pratiques des Modules PowerShell

Ce document constitue le guide de référence méthodologique et technique sur la conception, le packaging et l'industrialisation des modules sous PowerShell. Il détaille l'architecture modulaire standard en entreprise, le modèle de séparation « Public / Private », la configuration du manifeste de module (`.psd1`), le mécanisme d'auto-chargement (*Module Auto-loading*), ainsi que l'ensemble des règles d'ingénierie logicielle garantissant la portabilité, la sécurité et la maintenabilité des outils d'administration.

## 1. Introduction et Enjeux : Pourquoi Packager en Modules ?

Au stade initial de l'apprentissage ou du prototypage, l'administrateur système manipule des scripts autonomes (`.ps1`) stockés localement et appelés par leur chemin de fichier :

```powershell
.\audit_serveurs.ps1 -SeuilMo 200
```

### 1.1 Les limites des scripts (`.ps1`) en entreprise

*   **Dispersion et absence de gouvernance :** Les scripts sont éparpillés sur des partages réseau, des bureaux ou des machines locales, rendant impossible le suivi des versions.
*   **Absence d'isolation des fonctions internes :** Toutes les fonctions utilitaires (aide au calcul, parsing de logs) sont chargées dans la session de l'utilisateur ou doivent être dupliquées d'un script à l'autre (violation du principe DRY : *Don't Repeat Yourself*).
*   **Ergonomie dégradée :** L'opérateur doit impérativement connaître le chemin physique du script sur le disque au lieu de bénéficier de l'auto-complétion universelle de PowerShell (TAB).
*   **Fragilité des dépendances :** Impossible de déclarer formellement les prérequis d'exécution (version minimale de PowerShell, modules tiers requis, architecture de processeur).

### 1.2 La solution industrielle : Le Module PowerShell

Un module est un ensemble cohérent de fonctionnalités regroupées dans une structure normalisée. Lorsqu'un module est correctement installé :

*   **Ses commandes deviennent natives pour le système :** elles apparaissent dans `Get-Command` et s'auto-complètent au clavier.
*   Il charge son propre espace d'exécution (*Module Session State*), protégeant les variables globales de l'utilisateur.
*   Il **sépare rigoureusement** les fonctions exposées à l'utilisateur des fonctions techniques internes.
*   Il est identifié par une **version sémantique stricte** facilitant son cycle de mise à jour.

## 2. L'Arborescence Standard : Le Pattern « Public / Private »

En environnement professionnel, **il est formellement proscrit d'écrire un fichier monolithique de plusieurs milliers de lignes**.
Une telle pratique rend les revues de code Git illisibles, interdit le travail collaboratif simultané et complique la maintenance. La règle d'or consiste à adopter le pattern **« une fonction = un fichier »**.

### 2.1 Schéma architectural de l'arborescence

```text
MonModuleOutils/
├── MonModuleOutils.psd1        # Manifeste du module (carte d'identité, version, exports) 
├── MonModuleOutils.psm1        # Script module racine (chargeur dynamique / orchestrateur) 
├── Public/                     # Commandes exposées aux utilisateurs finaux 
│   ├── Get-InfoServeur.ps1 
│   ├── Set-ConformiteRegistre.ps1 
│   └── Restart-ServiceMetier.ps1 
├── Private/                    # Fonctions d'aide internes (masquées pour l'utilisateur) 
│   ├── Test-ConnexionReseau.ps1 
│   ├── Write-AuditJournal.ps1 
│   └── Resolve-CodeErreur.ps1 
└── Tests/                      # Suite de tests unitaires Pester
    ├── Public/ 
    │   └── Get-InfoServeur.Tests.ps1 
    └── MonModuleOutils.Tests.ps1
```

### 2.2 Rôles des répertoires clés

*   **`Public/`** : Héberge les commandes destinées à être appelées directement par les administrateurs et les outils tiers. Chaque fichier porte strictement le nom de la fonction qu'il contient (ex : `Get-InfoServeur.ps1` contient `function Get-InfoServeur { ... }`).
*   **`Private/`** : Héberge les fonctions utilitaires (*helpers*). Ces fonctions effectuent des tâches répétitives (journalisation, validation de format, calculs bas niveau). Elles ne sont jamais exportées et demeurent invisibles en dehors du module.
*   **`Tests/`** : Héberge les scénarios de test Pester garantissant la non-régression du code avant toute mise en production.

## 3. Le Script Module Racine (`.psm1`) et le Chargement Dynamique

Le fichier `.psm1` sert exclusivement d'**orchestrateur de chargement**. Il parcourt récursivement les sous-dossiers, intègre les scripts par inclusion (*dot-sourcing*) et configure la frontière d'exportation.

### 3.1 Code canonique du fichier `.psm1`

```powershell
# ==============================================================================
# Script Module : MonModuleOutils.psm1
# Orchestrateur de chargement dynamique
# ==============================================================================

# 1. Résolution de la racine du module 
$RacineModule = $PSScriptRoot

# 2. Chargement des fonctions privées (Helpers internes) 
$ScriptsPrives = Get-ChildItem -Path (Join-Path -Path $RacineModule -ChildPath 'Private\*.ps1') -ErrorAction SilentlyContinue 
foreach ($Fichier in $ScriptsPrives) { 
    try { 
        . $Fichier.FullName 
    } catch { 
        Write-Error "Échec critique du chargement de la fonction privée '$($Fichier.Name)' : $($_.Exception.Message)" 
    } 
}

# 3. Chargement des fonctions publiques (Commandes utilisateur) 
$ScriptsPublics = Get-ChildItem -Path (Join-Path -Path $RacineModule -ChildPath 'Public\*.ps1') -ErrorAction SilentlyContinue 
foreach ($Fichier in $ScriptsPublics) { 
    try { 
        . $Fichier.FullName 
    } catch { 
        Write-Error "Échec critique du chargement de la fonction publique '$($Fichier.Name)' : $($_.Exception.Message)"
    } 
}

# 4. Frontière d'encapsulation : Exportation stricte des fonctions publiques 
# Par conception, aucune fonction issue du dossier 'Private' n'est mentionnée ici. 
Export-ModuleMember -Function $ScriptsPublics.BaseName
```

### 3.2 Fonctionnement du Dot-Sourcing (`. $Chemin`)

Par défaut, l'exécution d'un script via `& $Chemin` s'effectue dans un sous-scope éphémère qui détruit les fonctions définies dès la fin de l'exécution.
L'opérateur point (`.`), appelé **Dot-Sourcing**, force l'interpréteur à exécuter le fichier directement au sein du scope du module courant, rendant les fonctions immédiatement disponibles pour les autres composants internes.

## 4. Le Manifeste de Module (`.psd1`) : La Carte d'Identité

Le fichier manifeste (`.psd1`) est un fichier de données PowerShell contenant une table de hachage standardisée. Il décrit l'identité, les dépendances et les autorisations du package.

### 4.1 Génération initiale via `New-ModuleManifest`

On ne crée jamais un fichier `.psd1` vierge manuellement. On utilise la cmdlet native conçue à cet effet :

```powershell
New-ModuleManifest -Path '.\MonModuleOutils\MonModuleOutils.psd1' `
                   -RootModule 'MonModuleOutils.psm1' `
                   -ModuleVersion '1.0.0' `
                   -Author 'Équipe Ingénierie Système' `
                   -CompanyName 'Entreprise Corp' `
                   -Description 'Module d''administration et de conformité du parc Windows.' `
                   -PowerShellVersion '5.1' `
                   -FunctionsToExport @('Get-InfoServeur', 'Set-ConformiteRegistre', 'Restart-ServiceMetier') `
                   -CmdletsToExport @() `
                   -VariablesToExport @() `
                   -AliasesToExport @()
```

### 4.2 Anatomie des directives critiques du manifeste

```powershell
@{
    # Fichier de script exécuté lors de l'import
    RootModule = 'MonModuleOutils.psm1'
    
    # Version sémantique (Majeur.Mineur.Correctif) 
    ModuleVersion = '1.0.0'
    
    # Identifiant unique universel (GUID généré une seule fois) 
    GUID = 'a8f9c1b2-3e4d-4a5b-8c6e-7f1a2b3c4d5e'
    
    # Auteur et société 
    Author = 'Équipe Ingénierie Système' 
    CompanyName = 'Entreprise Corp'
    
    # Prérequis stricts d'environnement 
    PowerShellVersion = '5.1' 
    DotNetFrameworkVersion = '4.5' 
    
    # Modules obligatoires requis avant chargement 
    RequiredModules = @() 
    
    # Liste explicite des éléments exportés (AUCUN JOKER '*') 
    FunctionsToExport = @( 
        'Get-InfoServeur', 
        'Set-ConformiteRegistre', 
        'Restart-ServiceMetier' 
    ) 
    
    # Verrouillage des éléments non utilisés 
    CmdletsToExport   = @() 
    VariablesToExport = @() 
    AliasesToExport   = @()
    
    # Métadonnées privées pour le catalogue d'entreprise 
    PrivateData = @{ 
        PSData = @{ 
            Tags = @('Audit', 'Conformite', 'Production') 
        } 
    } 
}
```

## 5. Déploiement et Résolution des Chemins (`$env:PSModulePath`)

Pour que PowerShell soit capable d'auto-découvrir et d'auto-charger un module sans exiger de l'administrateur qu'il saisisse un chemin absolu vers le `.psm1`, le module doit être installé dans l'un des répertoires référencés par la variable d'environnement `$env:PSModulePath`.

### 5.1 Les trois portées standards de `$env:PSModulePath`

```text
$env:PSModulePath (Séparé par des points-virgules sous Windows)
│
├── 1. Portée Utilisateur Courant (CurrentUser) 
│   └── C:\Users\<Nom>\Documents\WindowsPowerShell\Modules 
│
├── 2. Portée Machine / Tous les Utilisateurs (AllUsers) 
│   └── C:\Program Files\WindowsPowerShell\Modules 
│
└── 3. Portée Système / Système d'Exploitation (System)
    └── C:\Windows\System32\WindowsPowerShell\v1.0\Modules
```

| Portée | Emplacement standard | Droits requis | Cas d'usage en entreprise |
| :--- | :--- | :--- | :--- |
| **CurrentUser** | `$HOME\Documents\WindowsPowerShell\Modules` | Utilisateur standard | Développement local, tests, environnements sans élévation de privilèges. |
| **AllUsers** | `$env:ProgramFiles\WindowsPowerShell\Modules` | Administrateur local | **Standard d'entreprise :** Serveurs de rebond, modules d'infrastructure partagés. |
| **System** | `$env:SystemRoot\system32\WindowsPowerShell\v1.0\Modules` | SYSTEM / TrustedInstaller | Zone protégée : Réservée exclusivement aux composants intégrés de Windows. |

### 5.2 La règle du nommage de répertoire

Pour que le mécanisme d'auto-chargement (*Auto-loading*) fonctionne, PowerShell impose une contrainte stricte : **Le nom du dossier racine du module doit être strictement identique au nom du fichier `.psd1` et du fichier `.psm1`.**

**ARBORESCENCE CONFORME (Auto-loading fonctionnel) :**
```text
C:\Program Files\WindowsPowerShell\Modules\
└── ParcAudit\
    ├── ParcAudit.psd1
    └── ParcAudit.psm1
```

**ARBORESCENCES INVALIDES (Auto-loading bloqué) :**
```text
C:\Program Files\WindowsPowerShell\Modules\
└── ParcAudit_V1\             <-- Nom de dossier différent du nom de fichier
    ├── ParcAudit.psd1
    └── ParcAudit.psm1

C:\Program Files\WindowsPowerShell\Modules\
└── ParcAudit.psd1            <-- Fichier déposé directement à la racine sans conteneur
```

## 6. Les 10 Règles et Bonnes Pratiques de Conception

L'écriture d'un module d'entreprise impose une discipline stricte pour éviter les conflits et garantir la compatibilité ascendante.

### Règle 1 : Adopter strictement la nomenclature Verbe-Nom approuvée
PowerShell impose des verbes normalisés consultables via la commande `Get-Verb`.
*   **Proscrit :** `Check-Disque`, `Delete-Logs`, `Audit-Machine`, `DoBackup`.
*   **Conforme :** `Test-DisqueConformite`, `Remove-LogArchive`, `Get-MachineAudit`, `Backup-SystemState`.
*   **Conséquence d'un verbe non approuvé :** Déclenche un avertissement d'importation (`Warning: The verb ... is unapproved`) perturbant les pipelines d'automatisation.

### Règle 2 : Zéro formatage et zéro texte brut en sortie
Une fonction de module ne doit jamais appeler `Format-Table`, `Format-List`, `Out-Host` ou `Write-Host` pour renvoyer des données.
*   **Pourquoi :** Les cmdlets `Format-*` détruisent l'objet .NET vivant et le remplacent par des instructions typographiques de rendu pour la console. L'utilisateur final ne peut plus rien trier (`Sort-Object`), filtrer (`Where-Object`) ni exporter (`Export-Csv`).
*   **Bonne pratique :** Renvoyer exclusivement des objets métiers structurés de type `[PSCustomObject]`. Le formatage visuel appartient à l'utilisateur, pas au module.

### Règle 3 : Proscrire les jokers (*) dans FunctionsToExport
Dans le fichier `.psd1`, laisser `FunctionsToExport = '*'` force PowerShell à charger le code complet du module en mémoire vive dès qu'un utilisateur lance une commande ou demande l'auto-complétion.
*   **Bonne pratique :** Énumérer explicitement chaque fonction publique : `FunctionsToExport = @('Get-InfoServeur', 'Set-Configuration')`. Cela permet à PowerShell de construire une table de routage instantanée sans consommer de mémoire RAM tant que la commande n'est pas exécutée.

### Règle 4 : Cloisonnement strict des variables de portée (Scopes)
Un module ne doit jamais modifier l'espace global de l'utilisateur.
*   **Proscrit :** Affecter une variable avec `$global:Config = "..."`.
*   **Conforme :** Utiliser la portée script `$script:ConfigInterne = "..."` pour partager des informations d'état entre les différentes fonctions du module sans jamais polluer la console de l'administrateur.

### Règle 5 : Aide intégrée complète (Comment-Based Help)
Chaque fonction située dans `Public/` doit impérativement comporter un bloc d'aide documenté. Le minimum requis en production comprend :
*   `.SYNOPSIS` : Définition en une phrase de l'outil.
*   `.DESCRIPTION` : Fonctionnement technique détaillé.
*   `.PARAMETER` : Rôle et contraintes de chaque paramètre.
*   `.EXAMPLE` : Au moins deux exemples réels exploitables par les équipes d'exploitation.

### Règle 6 : Respecter l'idempotence et les actions destructrices (-WhatIf)
Toute fonction qui modifie l'état d'un système (création, suppression, modification de service ou de registre) doit :
1.  Activer la liaison avancée : `[CmdletBinding(SupportsShouldProcess = $true)]`.
2.  Encapsuler l'action dans une condition `if ($PSCmdlet.ShouldProcess($Cible, $Action))`.
3.  Neutraliser les invites secondaires sur les sous-commandes via `-Confirm:$false`.

### Règle 7 : Ne jamais altérer $ErrorActionPreference globalement
Un module ne doit jamais modifier la variable `$ErrorActionPreference` de la session parente.
Si une gestion d'erreur bloquante est nécessaire, appliquer localement `-ErrorAction Stop` sur la commande critique à l'intérieur d'un bloc `try / catch`.

### Règle 8 : Typage strict et validation en amont
Chaque paramètre d'une fonction publique doit être fortement typé (`[string]`, `[int]`, `[datetime]`) et protégé par des attributs de validation (`[ValidateNotNullOrEmpty()]`, `[ValidateSet()]`, `[ValidateRange()]`). Cela empêche l'exécution de code sur des données invalides.

### Règle 9 : Versioning Sémantique rigoureux (SemVer)
Tout module d'entreprise doit suivre la norme de versioning sémantique :
*   **Correctif (Patch - ex: 1.0.1) :** Corrections de bugs sans modification des paramètres existants.
*   **Mineur (Minor - ex: 1.1.0) :** Ajout de nouvelles fonctionnalités ou de nouveaux paramètres facultatifs en préservant la compatibilité avec l'existant.
*   **Majeur (Major - ex: 2.0.0) :** Rupture de compatibilité (*breaking change* : renommage d'une commande, suppression d'un paramètre, refonte d'un type de retour).

### Règle 10 : Gestion explicite des retours et pipeline
Si une fonction accepte des entrées depuis le pipeline, elle doit structurer son flux d'instructions autour des blocs `begin`, `process` et `end` pour traiter les données au fil de l'eau sans saturer la mémoire vive du poste.

## 7. Contrôle Qualité, Validation et Recette Opérationnelle

Avant de déployer un module sur des serveurs de production, l'administrateur doit suivre une procédure de validation normalisée en 4 étapes.

### 7.1 Étape 1 : Validation syntaxique du manifeste
La cmdlet `Test-ModuleManifest` analyse le fichier `.psd1` sans exécuter de code pour garantir sa validité :
```powershell
Test-ModuleManifest -Path '.\MonModuleOutils\MonModuleOutils.psd1'
```
Le retour doit afficher un objet décrivant le module. Toute anomalie de syntaxe, de version ou de fonction introuvable déclenche une erreur bloquante.

### 7.2 Étape 2 : Analyse statique avec PSScriptAnalyzer
L'analyse statique permet de vérifier la conformité du code avec les standards officiels de Microsoft :
```powershell
Invoke-ScriptAnalyzer -Path '.\MonModuleOutils' -Recurse
```
Cette commande relève automatiquement les verbes non approuvés, l'usage de variables non initialisées ou la présence d'alias proscrits (`dir`, `del`, `select`).

### 7.3 Étape 3 : Test d'importation en session vierge
Pour s'assurer qu'aucune variable locale de développement ne fausse le comportement du module :
1.  Ouvrir un terminal PowerShell vierge.
2.  Importer le module en mode verbeux pour observer les exports réels :
```powershell
Import-Module '.\MonModuleOutils\MonModuleOutils.psd1' -Verbose -Force
```

### 7.4 Étape 4 : Audit de visibilité et d'isolation
Vérifier que seules les fonctions prévues sont exposées et que les fonctions d'aide internes restent invisibles :

```powershell
# 1. Vérifier les commandes publiques exposées 
Get-Command -Module MonModuleOutils

# 2. Vérifier que les fonctions privées ne sont PAS accessibles
Get-Command Test-ConnexionReseau -ErrorAction SilentlyContinue # Doit renvoyer $null

# 3. Vérifier l'aide intégrée
Get-Help Get-InfoServeur -Detailed
```
