# **Corrigé du TP : Intégration AD du Bastion Linux (SSSD & Tiering)**

## **Le Prérequis Absolu (La résolution DNS)**

**Fichier modifié :** `/etc/systemd/resolved.conf` **Explication :** Sous Linux, l'authentification Active Directory ne fonctionne pas avec de simples adresses IP. Le démon `SSSD` utilise le protocole Kerberos (pour l'authentification) et LDAP (pour l'identité). Pour trouver le Contrôleur de Domaine, le Linux doit être capable de résoudre les enregistrements DNS spécifiques (les enregistrements SRV comme `_kerberos._tcp.formation.local`). Si le DNS ne pointe pas vers le DC Windows, la jonction est impossible.

## **La Jonction au Domaine**

**Commande exécutée :**

* sudo realm join \-U Administrateur formation.local

* **Sous le capot :** L'outil `realmd` a automatisé plusieurs tâches complexes :  
  1. Il a contacté le KDC (Key Distribution Center) du Contrôleur de Domaine pour obtenir un ticket Kerberos initial avec le compte Administrateur.  
  2. Il a créé un objet "Ordinateur" (Computer) dans l'Active Directory, exactement comme si c'était un serveur Windows.  
  3. Il a généré un fichier `/etc/krb5.keytab` contenant le secret partagé entre le Linux et le DC.  
  4. Il a configuré `SSSD` pour router les demandes d'authentification vers le domaine Windows.

## **Le Verrouillage ANSSI (Modèle en Tiers)**

C'est l'étape la plus critique du TP pour la sécurité.

**Commandes exécutées :**

* sudo realm deny \--all  
* sudo realm permit \-g "Admins\_LAPS\_Tier0@formation.local"

* **Le problème de base (Rupture du Tiering) :** Par défaut, après un `realm join`, **tous** les utilisateurs de l'Active Directory ont le droit d'ouvrir une session SSH sur le Linux. Un simple comptable (Tier 2\) pourrait s'y connecter. Même sans droits d'administration, il aurait un accès au shell (Terminal) d'un serveur critique (Tier 0).  
* **La solution SSSD :** La commande `deny --all` ferme la porte à tout le monde. La commande `permit` ajoute une exception stricte dans le fichier de configuration `/etc/sssd/sssd.conf`. Désormais, avant même de demander le mot de passe, SSSD vérifie si l'utilisateur appartient au groupe autorisé. Si ce n'est pas le cas, la connexion est rejetée net.

## **Création des profils et Élévation de privilèges (Sudo)**

**Modification de :** `/etc/sudoers.d/ad_admins` **Ligne ajoutée :** `%Admins_LAPS_Tier0@formation.local ALL=(ALL:ALL) ALL`

* **Explication du "Mapping" :** Les administrateurs AD se connectent sur le Linux en tant qu'utilisateurs standards. Pour leur donner le droit d'exécuter des commandes en tant que `root`, nous lions le groupe Active Directory au groupe `sudo` local.  
* **La syntaxe :** Le `%` au début de la ligne indique au fichier `sudoers` qu'il s'agit d'un groupe (et non d'un utilisateur isolé).

## **Le Crash-Test (Analyse des résultats)**

### **1\. La tentative avec le compte standard (`pirate`)**

* **Résultat :** Le serveur Linux a refusé la connexion (soit en fermant la session immédiatement, soit avec un message `Permission denied`).  
* **Conclusion :** Le verrouillage (Partie 4\) fonctionne parfaitement. Le module de sécurité PAM (Pluggable Authentication Modules) a interrogé SSSD, qui a interrogé l'AD. Le compte existe, mais il n'est pas dans le groupe autorisé. Le Tiering est respecté.

### **2\. La tentative avec le compte `Administrateur` du Domaine**

* **Résultat :** La session SSH s'est ouverte avec succès. Le système a affiché `Creating directory /home/Administrateur@formation.local`.  
* **Conclusion :**  
  * L'authentification Kerberos a fonctionné.  
  * Le module PAM `mkhomedir` (activé en Partie 5\) a généré le répertoire personnel à la volée lors de la première connexion.  
  * La commande `sudo su -` a réussi grâce au fichier `sudoers.d`, prouvant que l'élévation des privilèges est bien gérée de manière centralisée par votre forêt Active Directory.
