# TP — Mise à l'échelle horizontale, load balancing et résilience

## Objectifs

* Configurer Nginx et Docker Compose pour répartir le trafic sur plusieurs instances de l'API fil rouge.  
* Vérifier la répartition de charge et la cohérence des données partagées en base PostgreSQL.  
* Constater concrètement pourquoi un état conservé en mémoire locale casse le scaling horizontal.  
* Simuler la disparition d'un conteneur afin d'observer la tolérance aux pannes et les limites de Docker Compose face à un orchestrateur.  
* Concevoir une stratégie d'auto-scaling, de haute disponibilité et de reprise d'activité adaptée au Cloud.

## Étape 1 : Adapter la stack pour le scaling horizontal

Nous repartons du dossier `fil-rouge-stack`.

1. Vérifiez votre fichier `fil-rouge-stack/compose.yaml` et assurez-vous que le service `api` :  
   * ne contient aucune directive `container_name` ;  
   * ne publie aucun port sur la machine hôte (pas de section `ports`).  
   * Pourquoi ces deux contraintes sont-elles indispensables pour lancer plusieurs réplicas de `api` ?  
2. Modifiez le fichier `fil-rouge-stack/nginx/default.conf` afin que Nginx interroge dynamiquement le serveur DNS interne de Docker (`127.0.0.11`) avec un cache de 5 secondes et redirige les requêtes via une variable vers `http://api:5000`.  
3. Démarrez la stack avec **3 réplicas** du service `api` :

```sh
docker compose up -d --scale api=3
```

4. Vérifiez avec `docker compose ps` que vous disposez bien d'un conteneur `proxy`, d'un conteneur `db` (état `healthy`) et de **3 conteneurs `api`** actifs.

## Étape 2 : Tester le load balancing et la cohérence des données

1. Envoyez 9 requêtes successives vers la route `/` de votre reverse proxy et observez le champ `"host"` dans les réponses :

```sh
for i in $(seq 1 9); do
  curl -s http://localhost:8080/
  echo ""
done
```

   * Combien d'identifiants d'hôtes différents apparaissent ?  
   * Vérifiez que ces identifiants correspondent bien aux identifiants des 3 conteneurs `api` listés par `docker compose ps`.  
2. Insérez un élément en base de données via le load balancer :

```sh
curl -X POST http://localhost:8080/items \
  -H "Content-Type: application/json" \
  -d '{"name": "Test Load Balancing"}'
```

3. Interrogez la route `GET /items` plusieurs fois de suite :

```sh
for i in $(seq 1 6); do
  curl -s http://localhost:8080/items
  echo ""
done
```

   * Bien que les requêtes soient traitées par des conteneurs `api` différents, la réponse est-elle toujours identique ? Pourquoi ?

## Étape 3 : Observer le problème d'une application *stateful*

Pour voir concrètement ce qui se passe lorsqu'une application conserve un état en mémoire locale, vous allez ajouter temporairement un compteur de visites stocké dans une variable Python.

1. Dans `fil-rouge-stack/api/app.py`, ajoutez une variable globale `visits = 0` juste après `app = Flask(__name__)`, ainsi que la route suivante :

```py
@app.route("/visits")
def count_visits():
    global visits
    visits += 1
    return jsonify({"host": socket.gethostname(), "visits": visits})
```

2. Reconstruisez l'image `api` et redémarrez la stack avec toujours 3 réplicas :

```sh
docker compose up -d --build --scale api=3
```

3. Appelez la route `/visits` 9 fois de suite :

```sh
for i in $(seq 1 9); do
  curl -s http://localhost:8080/visits
  echo ""
done
```

   * Observez la valeur du champ `"visits"` au fil des appels : le compteur progresse-t-il normalement de 1 à 9 ?  
   * Que se passerait-il dans une vraie application si vous stockiez la session de connexion d'un utilisateur de la même façon en mémoire Python ?  
   * Quel type de service externe utiliseriez-vous pour rendre ce compteur (ou une session utilisateur) fiable malgré les 3 réplicas ?

## Étape 4 : Simuler la perte d'un conteneur et tester l'élasticité manuelle

1. Listez les conteneurs de la stack avec `docker compose ps` et relevez le nom complet de l'un des 3 conteneurs `api` (par exemple `fil-rouge-stack-api-1`).  
2. Supprimez brutalement ce conteneur pendant que la stack tourne :

```sh
docker rm -f <nom_du_conteneur_api>
```

3. Attendez 6 secondes (le temps que le cache DNS de 5 secondes configuré dans Nginx expire), puis relancez une série de requêtes sur `http://localhost:8080/` :

```sh
for i in $(seq 1 6); do
  curl -s http://localhost:8080/
  echo ""
done
```

   * L'application continue-t-elle de répondre sans erreur ?  
   * Combien d'hôtes différents répondent désormais ?  
4. Exécutez à nouveau `docker compose ps` :  
   * Combien de conteneurs `api` sont en cours d'exécution ?  
   * Docker Compose a-t-il automatiquement recréé un 3e conteneur pour rétablir l'état souhaité ?  
   * Que ferait un orchestrateur comme Kubernetes ou AWS ECS dans la même situation ?  
5. Simulez une baisse de trafic en ramenant manuellement le nombre d'instances à 1 :

```sh
docker compose up -d --scale api=1
```

   Vérifiez avec `docker compose ps` qu'un seul conteneur `api` subsiste.

## Étape 5 : Concevoir la résilience et le passage à l'échelle dans le Cloud

Vous devez maintenant préparer le passage en production de `fil-rouge-stack` dans le Cloud. Répondez aux quatre points suivants en justifiant vos choix :

1. **Identifier les points de défaillance uniques (SPOF)** :

   * Même avec 3 conteneurs `api`, quels composants de votre architecture locale restent des points de défaillance uniques ?  
   * Comment supprimer chacun de ces SPOF dans une architecture Cloud Multi-AZ ?  
2. **Paramétrer une règle d'auto-scaling** :

   * Proposez une configuration d'auto-scaling cohérente pour `fil-rouge-api` en précisant : la métrique surveillée, le seuil de déclenchement, le nombre minimum d'instances, le nombre maximum d'instances et la période de stabilisation (*cooldown*).  
   * Quel risque précis évite le plafond (`max`) ? Quel comportement instable évite le `cooldown` ?  
3. **Arbitrer entre Kubernetes managé, CaaS Serverless et FaaS** :

   * Pour héberger `fil-rouge-api` (une API simple gérée par deux développeurs), préférez-vous un cluster **Kubernetes managé** (EKS, AKS, GKE, Kapsule) ou un service **CaaS Serverless** (Cloud Run, ECS Fargate, Scaleway Serverless Containers) ? Pourquoi ?  
   * L'entreprise souhaite ajouter une fonctionnalité indépendante : chaque fois qu'un utilisateur dépose une photo dans un bucket S3, une petite tâche de 3 secondes doit générer une miniature. Pourquoi le modèle **FaaS** (AWS Lambda, Scaleway Functions, Cloud Functions) est-il particulièrement adapté à ce besoin précis, et quelles sont ses deux principales limites ?  
4. **Traduire des exigences de PRA (RPO / RTO)** :

   * Le métier exige un **RPO de 15 minutes** et un **RTO de 1 heure** pour l'application.  
   * Expliquez concrètement ce que ces deux chiffres impliquent pour la fréquence de sauvegarde (ou de réplication) de PostgreSQL et pour la procédure de remise en service après un sinistre majeur.

## Étape 6 : Nettoyage

1. Arrêtez la stack avec `docker compose down`.  
2. Vous pouvez retirer la route `/visits` et la variable `visits` de `fil-rouge-stack/api/app.py` afin de garder l'API propre pour les deux derniers segments.
