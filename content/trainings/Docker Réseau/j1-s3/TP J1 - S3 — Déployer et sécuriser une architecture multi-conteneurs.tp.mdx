# TP — Déployer et sécuriser une architecture multi-conteneurs

## Objectifs

* Comprendre comment Docker Compose assemble plusieurs services indépendants (reverse proxy, API, base de données) à partir d'un fichier unique.  
* Vérifier concrètement le cloisonnement réseau entre les couches d'une application.  
* Constater le comportement des données lors de la destruction et de la recréation des conteneurs (rôle des volumes nommés).  
* Identifier les erreurs courantes de sécurité et préparer la transposition d'une stack locale vers une architecture Cloud.

> **Mode d'emploi :** tous les fichiers de configuration et toutes les commandes sont fournis et expliqués ci-dessous. Votre travail consiste à les mettre en place dans l'ordre, observer les résultats retournés par Docker et répondre aux questions d'analyse.

## Étape 1 : Mettre en place l'architecture trois tiers

Créez les fichiers ci-dessous dans leurs dossiers respectifs.

### 1.1 Les fichiers du service API (`fil-rouge-stack/api/`)

**Fichier `api/requirements.txt`** (ajoute le pilote PostgreSQL en plus de Flask) :

```
flask==3.1.0
psycopg2-binary==2.9.10
```

**Fichier `api/.dockerignore`** :

```
.git
.gitignore
.env
README.md
Dockerfile*
__pycache__
*.pyc
```

**Fichier `api/Dockerfile`** :

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY app.py .

EXPOSE 5000

CMD ["python", "app.py"]
```

&nbsp;

**Fichier `api/app.py`** (ajoute la création d'une table `items`, la vérification de la connexion base de données sur `/health` et l'enregistrement d'éléments sur `/items`) :

```py
import os
import socket
import psycopg2
from flask import Flask, jsonify, request

app = Flask(__name__)

DATABASE_URL = os.getenv("DATABASE_URL")


def get_db_connection():
    return psycopg2.connect(DATABASE_URL)


def init_db():
    with get_db_connection() as conn:
        with conn.cursor() as cur:
            cur.execute(
                """
                CREATE TABLE IF NOT EXISTS items (
                    id SERIAL PRIMARY KEY,
                    name TEXT NOT NULL,
                    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
                );
                """
            )
        conn.commit()


@app.route("/")
def index():
    return jsonify(
        {
            "service": "fil-rouge-api",
            "version": os.getenv("APP_VERSION", "2.0"),
            "host": socket.gethostname(),
        }
    )


@app.route("/health")
def health():
    try:
        with get_db_connection() as conn:
            with conn.cursor() as cur:
                cur.execute("SELECT 1;")
        return jsonify({"status": "ok", "database": "connected"}), 200
    except Exception as exc:
        return jsonify({"status": "error", "detail": str(exc)}), 500


@app.route("/items", methods=["GET"])
def list_items():
    with get_db_connection() as conn:
        with conn.cursor() as cur:
            cur.execute("SELECT id, name, created_at FROM items ORDER BY id;")
            rows = cur.fetchall()
    return jsonify(
        [{"id": r[0], "name": r[1], "created_at": r[2].isoformat()} for r in rows]
    )


@app.route("/items", methods=["POST"])
def create_item():
    payload = request.get_json(silent=True) or {}
    name = payload.get("name")
    if not name:
        return jsonify({"error": "Le champ 'name' est requis"}), 400
    with get_db_connection() as conn:
        with conn.cursor() as cur:
            cur.execute(
                "INSERT INTO items (name) VALUES (%s) RETURNING id, name;", (name,)
            )
            row = cur.fetchone()
        conn.commit()
    return jsonify({"id": row[0], "name": row[1]}), 201


if __name__ == "__main__":
    init_db()
    port = int(os.getenv("PORT", "5000"))
    app.run(host="0.0.0.0", port=port)
```

### 1.2 La configuration du reverse proxy (`fil-rouge-stack/nginx/`)

**Fichier `nginx/default.conf`** (Nginx reçoit les requêtes sur le port `80` et les transmet au conteneur nommé `api` sur le port `5000`) :

```nginx
server {
    listen 80;

    location / {
        proxy_pass http://api:5000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

## Étape 2 : Décrire la pile complète dans `compose.yaml`

Créez le fichier `compose.yaml` à la racine de `fil-rouge-stack/` avec le contenu suivant :

```yaml
services:
  proxy:
    image: nginx:1.27-alpine
    ports:
      - "8080:80"
    volumes:
      - ./nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
    networks:
      - frontend
    depends_on:
      - api
    restart: unless-stopped

  api:
    build: ./api
    environment:
      APP_VERSION: "2.0"
      DATABASE_URL: "postgresql://${POSTGRES_USER}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB}"
    networks:
      - frontend
      - backend
    depends_on:
      db:
        condition: service_healthy
    restart: unless-stopped

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}
    volumes:
      - pgdata:/var/lib/postgresql/data
    networks:
      - backend
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER} -d ${POSTGRES_DB}"]
      interval: 5s
      timeout: 5s
      retries: 5
    restart: unless-stopped

networks:
  frontend:
  backend:

volumes:
  pgdata:
```

## Étape 3 : Valider, démarrer et tester l'application

Ouvrez un terminal dans le dossier `fil-rouge-stack`, puis exécutez les commandes suivantes dans l'ordre.

### 3.1 Vérifier la syntaxe et la résolution des variables

```sh
docker compose config
```

Cette commande contrôle que l'indentation YAML est valide et affiche la configuration finale après remplacement des variables `${POSTGRES_...}` par les valeurs de votre fichier `.env`.

### 3.2 Construire et lancer toute la pile

```sh
docker compose up -d --build
```

Décryptage :

* `up` : crée les réseaux, crée le volume, construit les images nécessaires et démarre tous les conteneurs dans le bon ordre ;  
* `-d` : exécute l'ensemble en arrière-plan ;  
* `--build` : construit l'image du service `api` à partir de `./api/Dockerfile`.

Vérifiez ensuite l'état de chaque service :

```sh
docker compose ps
```

Assurez-vous que le service `db` indique `(healthy)` et que `api` et `proxy` sont actifs (`Up`).

### 3.3 Tester les échanges de bout en bout

Ouvrez `http://localhost:8080/health` dans votre navigateur (ou utilisez `curl` dans le terminal) :

```sh
curl http://localhost:8080/health
```

Vous devez obtenir `{"database":"connected","status":"ok"}`.

Enregistrez maintenant deux éléments en base de données en envoyant deux requêtes HTTP `POST` via le reverse proxy :

```sh
curl -X POST http://localhost:8080/items \
  -H "Content-Type: application/json" \
  -d '{"name": "Conteneurisation"}'
```

&nbsp;

```sh
curl -X POST http://localhost:8080/items \

```

Vérifiez que les deux éléments sont bien enregistrés en ouvrant `http://localhost:8080/items` dans votre navigateur ou via :

```sh
curl http://localhost:8080/items
```

Consultez enfin les journaux des services `proxy` et `api` pour suivre le trajet de vos requêtes :

&nbsp;


## Étape 4 : Vérifier le cloisonnement réseau

Dans notre fichier `compose.yaml`, `proxy` n'est relié qu'au réseau `frontend`, tandis que `db` n'est relié qu'au réseau `backend`. Seule `api` fait le pont entre les deux.

Vous allez tester concrètement si le reverse proxy peut joindre l'API, puis s'il peut joindre la base de données.

### 4.1 Tester les flux depuis le conteneur `proxy`

La commande `nc -zv` (*netcat*) vérifie simplement si un port réseau est joignable depuis un conteneur donné :

```sh
# Test 1 : proxy -> api (sur le réseau frontend)
docker compose exec proxy nc -zv api 5000
```

&nbsp;

```sh
# Test 2 : proxy -> db (sur le réseau backend, interdit)
docker compose exec proxy nc -zv db 5432
```

### 4.2 Consulter directement la base de données pour vérification

Pour confirmer que la base contient bien vos données malgré l'absence de port exposé sur votre poste, interrogez PostgreSQL depuis l'intérieur du conteneur `db` :

```sh
docker compose exec db psql -U filrouge -d filrouge_db -c "SELECT * FROM items;"
```

**Questions d'analyse :**

1. Quel est le résultat du test 1 (`proxy` vers `api:5000`) par rapport au test 2 (`proxy` vers `db:5432`) ?  
2. Si une faille de sécurité permettait un jour à un attaquant de prendre le contrôle du serveur web en façade (`proxy`), en quoi cette séparation en deux réseaux limite-t-elle l'impact sur les données de l'entreprise ?

## Étape 5 : Vérifier la persistance des données

Un conteneur est jetable, mais les données métier doivent survivre aux redémarrages et aux mises à jour. Vous allez comparer deux façons d'arrêter une pile Compose : avec et sans l'option `-v`.

### 5.1 Supprimer les conteneurs en conservant le volume (`down`)

Arrêtez et supprimez tous les conteneurs et réseaux du projet :

```sh
docker compose down
```

Vérifiez qu'il ne reste plus de conteneurs actifs, mais que le volume de la base de données existe toujours :

```sh
docker ps -a
```

&nbsp;

```sh
docker volume ls
```

Redémarrez maintenant toute la pile et interrogez à nouveau `/items` :

```sh
docker compose up -d
```

&nbsp;

```sh
curl http://localhost:8080/items
```

### 5.2 Supprimer les conteneurs ET les volumes (`down -v`)

Exécutez maintenant la même opération en ajoutant l'option `-v` (volumes) :

```sh
docker compose down -v
```

Redémarrez la pile et interrogez à nouveau `/items` :

```sh
docker compose up -d
```

&nbsp;

```sh
curl http://localhost:8080/items
```

**Questions d'analyse :**

1. Après `docker compose down` (sans `-v`), vos deux éléments enregistrés à l'étape 3 étaient-ils toujours présents après le redémarrage ? Pourquoi ?  
2. Que s'est-il passé après `docker compose down -v` ?  
3. Dans le cadre d'un projet, dans quelle situation l'option `-v` est-elle utile, et dans quelle situation représente-t-elle un risque majeur ?
