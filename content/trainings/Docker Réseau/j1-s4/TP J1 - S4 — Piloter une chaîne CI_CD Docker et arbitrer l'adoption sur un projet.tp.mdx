# TP — Piloter une chaîne CI/CD Docker et arbitrer l'adoption sur un projet

## Objectifs

* Diagnostiquer des dysfonctionnements courants dans une chaîne de livraison logicielle et poser un contrat clair entre équipes Dev et Ops.  
* Savoir lire un fichier de pipeline CI/CD réel (GitHub Actions) pour vérifier ses garde-fous qualité et sécurité.  
* Choisir le bon niveau d'automatisation (CI, Livraison Continue, Déploiement Continu) selon la criticité d'un projet.  
* Arbitrer de manière argumentée l'adoption ou le refus de Docker face à différents contextes métiers.  
* Poser les bonnes exigences de sécurité et d'industrialisation pour le passage vers le Cloud.

## Atelier 1 : Diagnostiquer un incident de livraison et poser le contrat Dev / Ops

### Mise en situation

Vous reprenez le pilotage d'un projet web développé par un prestataire externe. Lors des derniers mois, trois problèmes se sont répétés :

* L'équipe construit une première image `projet-api:recette` pour les tests métiers, puis reconstruit une seconde image `projet-api:prod` la veille de la mise en production. Lors de la dernière livraison, l'application validée en recette a planté en production à cause d'une bibliothèque Python mise à jour entre les deux builds.  
* Lors de cet incident, les développeurs affirment que *« le code est bon »* et renvoient la faute sur l'équipe d'infrastructure, qui répond que *« les dépendances manquantes n'étaient pas documentées »*.  
* À chaque arrivée d'un nouveau développeur, il faut une journée complète pour installer le poste de travail en suivant une documentation souvent obsolète.

### Questions d'analyse

1. **Cycle *Build, Ship, Run* :** quel principe clé du cours n'est pas respecté dans la façon dont le prestataire construit ses images pour la recette et la production ? Comment l'équipe doit-elle procéder pour adapter une seule et même image à deux environnements différents (recette et production) ?  
2. **Contrat Dev / Ops :** en vous appuyant sur l'approche DevOps apportée par Docker, quelle répartition claire des responsabilités devez-vous fixer entre les **développeurs (Dev)** et l'**équipe d'infrastructure (Ops)** pour éviter ce renvoi de responsabilité ?  
3. **Intégration (*onboarding*) :** en quoi Docker et Docker Compose permettent-ils de ramener l'installation d'un nouveau poste développeur d'une journée à quelques minutes ? Quelles sont les grandes étapes que le nouvel arrivant aura simplement à suivre ?

## Atelier 2 : Auditer un pipeline CI/CD réel

### Mise en situation

Avant de valider le passage en industrialisation de l'application fil rouge, l'équipe technique vous soumet son fichier de pipeline **GitHub Actions** (`.github/workflows/ci.yml`) :

```yaml
name: CI-CD API Fil Rouge

on:
  push:
    branches: [ "main" ]
  pull_request:
    branches: [ "main" ]

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}/fil-rouge-api

jobs:
  build-and-test:
    runs-on: ubuntu-latest

    steps:
      - name: Récupérer le code source
        uses: actions/checkout@v4

      - name: Construire l'image Docker
        run: |
          docker build -t ${{ env.IMAGE_NAME }}:${{ github.sha }} ./api

      - name: Lancer les tests unitaires dans le conteneur
        run: |
          docker run --rm ${{ env.IMAGE_NAME }}:${{ github.sha }} python -m unittest discover -s tests

      - name: Smoke test de la stack complète
        run: |
          cp .env.example .env
          docker compose up -d --build
          sleep 5
          curl http://localhost:8080/health
          docker compose down -v

      - name: Connexion au registre
        if: github.event_name == 'push' && github.ref == 'refs/heads/main'
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Publier l'image sur le registre
        if: github.event_name == 'push' && github.ref == 'refs/heads/main'
        run: |
          docker tag ${{ env.IMAGE_NAME }}:${{ github.sha }} ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }}
          docker push ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }}
```

&nbsp;

### Questions d'audit

1. **Étape manquante :** parmi les étapes types d'un pipeline Docker vues dans le cours, une première étape de vérification statique (*lint*) est absente avant le build. Quel est son rôle, et quels outils (pour Python et pour le `Dockerfile`) pourriez-vous recommander à l'équipe ?  
2. **Anomalie cachée dans le smoke test :** examinez attentivement la ligne `curl http://localhost:8080/health`. Une option essentielle a été oubliée dans ce fichier. Laquelle, et quel risque concret crée cet oubli si l'API renvoie une erreur HTTP `500` ou `404` ?  
3. **Garde-fous avant publication :**  
   * Lorsqu'un développeur ouvre une *Pull Request* vers `main`, les étapes de connexion et de publication (`push`) sont-elles exécutées ? Pourquoi ?  
   * Que doit faire le pipeline si l'étape de tests unitaires échoue, et quelle garantie cela apporte-t-il pour la production ?  
4. **Traçabilité et sécurité :**  
   * Pourquoi est-il pertinent d'étiqueter l'image avec `${{ github.sha }}` plutôt qu'avec `:latest` ?  
   * Quel est le rôle de `${{ secrets.GITHUB_TOKEN }}` dans ce fichier ?  
5. **Choix d'outillage :** la direction technique hésite encore entre **GitHub Actions**, **GitLab CI** et **Jenkins** (déjà présent en interne). Quelle charge opérationnelle spécifique à **Jenkins** devez-vous mettre en avant dans le comparatif ?

## Atelier 3 : Choisir le bon niveau d'automatisation (CI / CD)

### Mise en situation

Vous accompagnez trois projets différents dans votre organisation :

* **Contexte 1 — Portail citoyen d'un organisme public :** chaque mise en production nécessite un feu vert formel de la maîtrise d'ouvrage après recette, mais l'équipe souhaite que l'image validée soit automatiquement construite, testée et prête à être déployée sur simple validation humaine.  
* **Contexte 2 — Service numérique grand public très mature :** l'équipe dispose d'une couverture de tests automatisés très complète et souhaite que chaque correctif validé par le pipeline parte automatiquement en production sans aucune action manuelle.  
* **Contexte 3 — Projet en démarrage :** l'équipe souhaite d'abord sécuriser la fusion quotidienne du code des développeurs pour détecter les régressions quelques minutes après leur introduction, sans encore automatiser la publication ni le déploiement.

### Questions d'analyse

1. Associez chaque contexte à la pratique adaptée (**Intégration Continue**, **Livraison Continue** ou **Déploiement Continu**) et justifiez précisément votre choix.  
2. Si une anomalie est finalement constatée juste après une mise en production, comment l'usage d'images Docker versionnées dans un registre facilite-t-il le retour arrière (*rollback*) ?
