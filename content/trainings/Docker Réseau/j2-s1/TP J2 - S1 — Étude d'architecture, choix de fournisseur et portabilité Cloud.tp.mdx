# TP — Étude d'architecture, choix de fournisseur et portabilité Cloud

## Objectifs

* Comparer concrètement la charge technique entre IaaS, CaaS et PaaS pour héberger l'application fil rouge (`fil-rouge-stack`).  
* Sélectionner un modèle de déploiement, un modèle de service et un fournisseur Cloud adaptés à des contraintes de budget, de compétences et de souveraineté.  
* Identifier les risques de vendor lock-in dans une architecture existante et proposer des mesures de réversibilité réalistes.  
* Vérifier en local la portabilité de l'application fil rouge et de sa base PostgreSQL.

## Étape 1 : Décliner l'application fil rouge en IaaS, CaaS et PaaS

Vous devez déployer l'application `fil-rouge-stack` (reverse proxy, API Python Flask, base PostgreSQL) dans le Cloud. Trois options d'architecture sont sur la table :

* **Option 1 (IaaS)** : déploiement de toute la pile avec Docker Compose sur une machine virtuelle Linux.  
* **Option 2 (CaaS \+ PaaS BDD)** : déploiement de l'image `fil-rouge-api` sur un service de conteneurs sans gestion de cluster (type Cloud Run, ECS Fargate ou Scaleway Serverless Containers) \+ base PostgreSQL managée.  
* **Option 3 (PaaS complet)** : déploiement direct du code source Python (sans Docker) sur une plateforme PaaS \+ base PostgreSQL managée.

Pour chacune des tâches suivantes, indiquez qui en a la responsabilité (**Client** ou **Fournisseur**) dans les trois options :

| Tâche technique | Option 1 (IaaS) | Option 2 (CaaS \+ PaaS BDD) | Option 3 (PaaS complet) |
| :---- | :---: | :---: | :---: |
| Maintenance du matériel et du datacenter |  |  |  |
| Mises à jour de sécurité du système Linux hôte |  |  |  |
| Configuration et renouvellement du certificat HTTPS (reverse proxy) |  |  |  |
| Mise à jour de la version de Python et des dépendances (`requirements.txt`) |  |  |  |
| Sauvegardes quotidiennes et restauration de PostgreSQL |  |  |  |
| Surveillance de l'espace disque de la base de données |  |  |  |

Questions d'analyse :

## Étape 2 : Arbitrer trois scénarios d'hébergement Cloud

Pour chacun des trois contextes suivants, proposez une architecture précise pour héberger `fil-rouge-stack` :

* **Modèle de déploiement** (Cloud public, privé, hybride ou multi-cloud) ;  
* **Modèles de services** pour l'API et la base de données ;  
* **Fournisseur retenu** (parmi AWS, Azure, GCP, OVHCloud, Scaleway) et **noms exacts des services** (registre d'images, exécution de l'API, base PostgreSQL, stockage de fichiers si nécessaire) ;  
* **Justification** basée sur les critères du projet.

### Scénario A — Portail pour un établissement public français

* **Contexte** : l'application traite des données administratives sensibles de citoyens français. La direction impose que les données restent en France et exige une immunité face aux lois extraterritoriales américaines (Cloud Act), idéalement avec une qualification SecNumCloud ou un acteur souverain français.  
* **Équipe** : deux développeurs qui maîtrisent Docker et PostgreSQL, mais pas Kubernetes.  
* **Trafic** : modéré et prévisible en journée, presque nul la nuit.

### Scénario B — Service interne pour un grand groupe industriel

* **Contexte** : l'entreprise utilise déjà Microsoft 365, Entra ID (Active Directory) pour tous ses collaborateurs et possède un datacenter privé où tourne son ERP historique. La nouvelle API fil rouge doit pouvoir interroger cet ERP interne de manière sécurisée tout en étant accessible aux commerciaux nomades.  
* **Équipe** : équipe IT structurée, habituée à l'écosystème Microsoft et à Docker.  
* **Contrainte** : facturation intégrée au contrat Cloud existant du groupe.

### Scénario C — Produit SaaS d'une jeune startup européenne

* **Contexte** : la startup lance un nouveau produit et ne sait pas encore quel volume de trafic elle aura le premier mois (peut-être 10 requêtes par jour, ou un pic soudain suite à une campagne). Le budget initial est très limité : elle veut payer au plus près de sa consommation réelle et livrer très vite.  
* **Équipe** : trois développeurs full-stack à l'aise avec Docker et GitHub Actions, aucune personne dédiée à l'infrastructure.  
* **Contrainte** : données hébergées en Union européenne (conformité RGPD), sans exigence SecNumCloud.

## Étape 4 : Vérifier la portabilité de `fil-rouge-stack` en local

Pour constater concrètement ce qu'apporte le choix de standards ouverts (Docker \+ PostgreSQL), vous allez simuler une migration de base de données entre deux environnements distincts sur votre poste, sans modifier une seule ligne de code de l'API.

1. Placez-vous dans votre dossier `fil-rouge-stack` et démarrez la stack :

```sh
docker compose up -d
```

2. Insérez deux éléments dans l'API afin d'avoir des données à migrer :

```sh
curl -X POST http://localhost:8080/items \
  -H "Content-Type: application/json" \
  -d '{"name": "Migration Cloud"}'

curl -X POST http://localhost:8080/items \
  -H "Content-Type: application/json" \
  -d '{"name": "Portabilite PostgreSQL"}'
```

3. Exportez le contenu de la base PostgreSQL dans un fichier SQL standard (`backup.sql`) à l'aide de `pg_dump` :

```sh
docker compose exec db pg_dump -U filrouge -d filrouge_db > backup.sql
```

   Ouvrez `backup.sql` (ou affichez-le avec `cat backup.sql`) : vérifiez qu'il s'agit de SQL standard lisible, indépendant de tout fournisseur.

4. Simulez le basculement vers un nouvel hébergeur vierge : détruisez complètement la stack et son volume (`docker compose down -v`), puis redémarrez une stack neuve (`docker compose up -d`).  
5. Vérifiez avec `curl http://localhost:8080/items` que la nouvelle base est bien vide (`[]`).  
6. Restaurez vos données dans la nouvelle base avec `psql` :

```sh
cat backup.sql | docker compose exec -T db psql -U filrouge -d filrouge_db
```

7. Interrogez à nouveau `curl http://localhost:8080/items` :  
   * Vos deux éléments sont-ils revenus ?  
   * Avez-vous eu besoin de reconstruire l'image Docker ou de modifier `app.py` ?  
8. Supprimez le fichier temporaire `backup.sql` et arrêtez la stack (`docker compose down`).

Imaginez que vous devez résumer en 5 lignes votre recommandation d'hébergement pour `fil-rouge-stack` à un directeur informatique qui hésite entre :

* acheter un serveur physique pour l'installer dans les locaux de l'entreprise (*on-premise*) ;
